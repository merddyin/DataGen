# Normalized Export

`Export-SEEnterpriseWorld` with the `Normalized` profile is the main downstream integration seam.

## Why normalized export is the right seam

It gives you:

- consistent file-oriented artifacts
- explicit entity and relationship shapes
- a cleaner contract for bridges and import adapters

## Typical export invocation

```powershell
$world | Export-SEEnterpriseWorld `
  -OutputPath .\out\normalized `
  -Format Json `
  -Profile Normalized `
  -IncludeManifest `
  -IncludeSummary `
  -Overwrite
```

## What to expect

The export set can include artifacts for:

- organizations, geography, and identity
- infrastructure and software
- applications and services
- repositories and collaboration
- policies and access evidence
- CMDB and observed views

Treat these artifacts as the source for your downstream bridge, not as something to re-synthesize later.

## Management observation history

The `endpoint_management_observations` artifact contains provider-neutral management facts for scenarios that opt into management observations. When population coverage is enabled, generation selects ordinary endpoints by operating-system and endpoint cohort, using a dominant management surface plus bounded stale, missing, alternate-provider, and hosted-compute fallback cases. This is lifecycle evidence, not a downstream vendor integration contract.

### Fields for lifecycle processing

Use these normalized fields together:

- `lifecycle_state`: `Current` or `Historical`
- `is_current`: the explicit currentness discriminator
- `superseded_by_observation_id`: the current observation that governs a historical row; empty for current rows
- `observed_at_utc` and `last_check_in_at_utc`: the chronological evidence, not lifecycle discriminators

Do not classify a row as historical just because it is unreachable or has an old check-in. Those fields describe the observation's operating condition; lifecycle, currentness, and supersession are explicit.

### Population coverage and chronology

`infrastructure.representativeManagementObservationCount` remains the explicit enablement switch: `0` suppresses management observations. `infrastructure.managementObservationPopulationCoveragePercentage` defaults to `0`, preserving the legacy per-company representative count. Set coverage to `1` through `100` to opt into deterministic, per-company selection within operating-system and endpoint cohorts. Coverage rounds each non-empty cohort up, so a nonzero percentage always selects at least one endpoint; `100` emits one current observation for every generated device and server.

Rare cases use floor-based limits so small cohorts are not distorted: missing management is at most `1%` and first appears at 100 selected endpoints; stale check-in and alternate-provider cases are each at most `2%` and first appear at 50 selected endpoints; hosted-compute fallback is at most `2%` of selected hosted endpoints and likewise first appears at 50. A lone hosted server therefore keeps its cohort's dominant management provider.

`infrastructure.representativeManagementHistoryObservationCount` is a separate, additional per-company history limit; set it to `0` to suppress history. With a fixed scenario, seed, and generated timestamp, selection and timestamps are deterministic. Build an ordered timeline from `observed_at_utc`, then `id` as a tie breaker, rather than trusting file row order.

## Policy-setting source timestamps

The `policy_settings` artifact includes `when_created`, `when_modified`, `observed_at`, and `retrieved_at`. DataGen completes missing values during generation from the supplied `GenerationContext.GeneratedAt` and stable record inputs, preserving any timestamp a source generator already supplied. The chronology is always `when_created <= when_modified <= observed_at <= retrieved_at`.

The additive columns advance the normalized export schema from `2.0.0` to `2.1.0`. Missing timestamps are projected within neighboring explicit bounds before external plugin execution. Inconsistent explicit chronology rejects generation transactionally, leaving the complete policy-setting collection unchanged.

These are source-side facts. A downstream bridge should preserve or reject them according to its provenance policy; it must not substitute its own runtime clock for a missing source timestamp.

### Consumer compatibility

Existing adapters that need only a current state can filter `is_current = true` and otherwise keep their current mapping. Adapters that need history should retain both rows, relate historical rows through `superseded_by_observation_id`, and keep provider-specific interpretation outside DataGen. The lifecycle columns are additive; when consuming an export produced before v0.10.0, treat absent lifecycle metadata as a current-only dataset rather than fabricating history.

## Windows security policy families

The `policies` and `policy_settings` artifacts carry three Windows policy families — privilege-rights assignments, advanced audit subcategories, and file and registry security descriptors — on two sides of the same estate.

The directory side is two `GroupPolicyObject` records per company, linked to the workstation and server containers:

- `Windows Security Template Baseline`, category `SecurityTemplate`, carrying privilege rights and object security descriptors
- `Windows Advanced Audit Policy Template`, category `AuditPolicy`, carrying advanced audit subcategories

The endpoint side is one `LocalSecurityPolicy` record per selected Windows endpoint, category `EffectiveConfiguration` and platform `Windows`, named for the endpoint's hostname. Join it back to its endpoint through the columns `policies` already exports:

- `source_entity_type`: `ManagedDevice` for a workstation, `ServerAsset` for a server
- `source_entity_id`: the identifier of that endpoint record

Only Windows endpoints carry one. A local security policy is a Windows object, so a Linux or macOS endpoint has no such record rather than an empty one.

### Canonical setting keys

`policy_settings.policy_path` carries a canonical prefixed key for every row in these families, on both sides. The same key identifies the same setting on a template and on an endpoint, which is what makes the two joinable:

| Family | `policy_path` form | Example |
| --- | --- | --- |
| Privilege rights | `UserRight:<PrivilegeConstant>` | `UserRight:SeBackupPrivilege` |
| Advanced audit | `Audit:<SubcategoryDisplayName>` | `Audit:Audit Credential Validation` |
| File security | `FileACL:<path>` | `FileACL:%SystemRoot%\System32\config` |
| Registry security | `RegistryACL:<key>` | `RegistryACL:MACHINE\SYSTEM\CurrentControlSet\Services` |

The leading word `Audit` is part of the subcategory display name itself, so an audit key reads as doubled — `Audit:Audit Logon`. That is the real subcategory name as a Group Policy audit backup spells it.

Key off `policy_path`, not `setting_category`. `setting_category` describes the family — `UserRightsAssignment`, `AuditPolicy`, `FileSecurity`, `RegistryKeys` — and is not a setting identifier.

### Values follow the collection method

Every value in these families is written in the shape produced by the tool that collects it, not in a normalized form:

- **Audit inclusion settings** use the vocabulary of the tool that collected them: `No Auditing`, `Success`, `Failure`, and a combined value that is spelled two different ways depending on the collection route. Both spellings are emitted; see [Both spellings of a combined audit value](#both-spellings-of-a-combined-audit-value) for which route produces which.
- **Principals** are the display names a collection resolves them to. Well-known identities use curated names — `BUILTIN\Administrators`, `BUILTIN\Users`, `Authenticated Users`, `Local System`, `Local Service`, `Network Service`, `Creator Owner`, `Everyone`, `Anonymous`. Identities outside that set use the live Windows translation, so the deny-logon rights carry forms such as `NT AUTHORITY\Local account` and `NT AUTHORITY\Local account and member of Administrators group`, upper-case and sentence-case inconsistencies included. Generated domain principals use the `NETBIOS\SamAccountName` form and resolve to real groups and accounts in the same company. Bare SIDs are never emitted, because a collection on a Windows host does not produce them.
- **Multiple principals** on one right are joined with a comma and no space. A right granted to nobody carries an empty value, matching `secedit` output.
- **Security descriptors** are ordinary SDDL strings in the usual owner, group, and DACL container, with inherited, explicit, and deny entries present.

These forms are a deliberate mirror of what a real collection returns. If the collection method's resolution behavior changes upstream, the emitted values change with it as a documented breaking change; they are not an independent DataGen vocabulary.

### Both spellings of a combined audit value

A combined audit value has two real spellings, and a row carries the one its collection route writes.

These two are the real spellings, not the only strings a generated world contains. Read the table below as the reference shapes rather than as an inventory of the export.

| Value | Collection route | `setting_category` | `source_system` | `source_reference` |
| --- | --- | --- | --- | --- |
| `Success and Failure` | a Group Policy backup's `audit.csv`, and `auditpol` | `AuditPolicy` | `AuditCsv` | `Group Policy audit backup audit.csv` |
| `Success, Failure` | a Group Policy report export, which carries the numeric code `3` that a report reader renders with a comma | `AuditPolicyReport` | `GPO` | `Group Policy report export gpreport.xml` |

Neither spelling is normalized into the other, and a row's spelling and its recorded source always agree: a row carrying the comma form resolves to the report source, never to the backup source.

The two spellings live on separate policy objects rather than on two copies of one configuration. `Windows Advanced Audit Policy Template` carries all 34 subcategories in the backup spelling. `Domain Controller Audit Baseline` is an additional `GroupPolicyObject` per company, category `AuditPolicy`, linked to that company's `Domain Controllers` container, carrying the 14 subcategories a domain controller audit policy sets, in the report spelling. Restating one configuration in a second spelling would assert that an estate holds it twice, which is not a fact; collecting different policy objects by different routes is what an estate actually does.

`policy_path` is unaffected by the route. Both baselines build an audit key the same way, so the same subcategory carries the same `Audit:<SubcategoryDisplayName>` key on both objects and only the value differs.

#### Legacy audit values retained outside those two spellings

A generated world also contains the string `Success,Failure`, with no space, on policy objects that predate the canonical baselines. It is not one of the two spellings above and no collection route writes it. These objects are preserved deliberately, so that a consumer built against an earlier release keeps reading the values it already reads; they are legacy output rather than a reference shape, and nothing here should be treated as the form a tool produces.

It is emitted unconditionally, at 24 sites per company across four policy objects:

| Policy object | Settings carrying `Success,Failure` |
| --- | --- |
| `Windows Advanced Audit Baseline` | 19 of its 37 settings |
| `Security Audit and Logging Baseline` | 3 |
| `Default Domain Policy` | 1 |
| `Target Server Security Baseline` | 1 |

Note the string differs from the real `Success, Failure` by the space: the spaced form is what a Group Policy report export writes, and it carries the report source accordingly. When you model audit values, take `Windows Advanced Audit Policy Template` and `Domain Controller Audit Baseline` as the reference objects and treat the values above as the legacy output they are.

### Configuration profiles

On the endpoint side, `policy_settings.source_reference` names the profile that endpoint's value was built from. Each value is derived from the template's own value for the same key, so the relationship is exact rather than incidental:

| `source_reference` | Shape of the emitted value |
| --- | --- |
| `Aligned` | Identical token set or audit value to the template |
| `ExpandedPrincipals` | Strict superset of the template's principals on a grant right |
| `ReducedPrincipals` | Strict, non-empty subset on a grant right |
| `DivergentPrincipals` | Overlapping on a grant right, neither superset nor subset |
| `ExpandedDenyPrincipals` | Strict superset on a deny-logon right |
| `ReducedAuditCoverage` | One outcome where the template covers both |
| `ExpandedAuditCoverage` | Both outcomes where the template covers one |
| `DivergentAcl` | A different security descriptor for the same object, alongside identical descriptors elsewhere |

A profile describes the shape of the data emitted for that endpoint. It is not a rating of the machine, and DataGen draws no conclusion from it. On the directory side, `source_reference` carries the originating section instead, such as `Security template [Privilege Rights]` or `Group Policy audit backup audit.csv`.

### Enabling the endpoint side

`infrastructure.effectiveSecurityConfigurationEndpointCount` is the explicit enablement switch. It defaults to `0`, which emits no `LocalSecurityPolicy` records, and is bounded at `250`. Scenario validation rejects a value outside that range, and rejects a nonzero value when the scenario includes neither workstations nor servers, or when the largest company's employee count cannot supply that many endpoints.

The shipped example scenarios set it, so a dataset generated from one of them carries both sides of these families. A company with fewer Windows endpoints than requested reports on every endpoint it has; endpoints are never invented to reach the count, and fewer profiles are covered as a result.

The directory-side templates need no option. They are ordinary facts of a Windows estate and are emitted for every company.

### Consumer compatibility

This family added no column of its own. Endpoint linkage reuses `source_entity_type` and `source_entity_id`, which `policies` already exported, and the canonical keys reuse `policy_path`, which `policy_settings` already exported. An adapter written against an earlier export continues to read these artifacts without modification. v0.13.0 as a whole did add columns elsewhere and advanced the schema version accordingly; see [Export schema 2.2.0](#export-schema-220).

The new records are additive. The friendly-named Windows baselines emitted before v0.13.0 are unchanged and still present, so an adapter reading them keeps working; the canonical-key rows live in separate policy objects rather than inside those baselines. An adapter that wants only the directory side can filter on a `policy_type` of `GroupPolicyObject`, and one that wants only endpoint configuration can filter on `LocalSecurityPolicy`. An export produced before v0.13.0 contains no `LocalSecurityPolicy` rows at all; treat their absence as a dataset without an endpoint side rather than as endpoints reported to have no configuration.

## Directory account name evidence

The `accounts` artifact carries the raw name attributes a directory object holds, alongside the `display_name` it already exported:

- `given_name` and `surname`: the name attributes as the object carries them
- `description`: what the object is for, in the object's own words

Which of these an account carries follows what the object is, not what would be convenient to read:

| Account class | `given_name` and `surname` | `description` |
| --- | --- | --- |
| Person-backed — user, secondary, privileged, guest, contractor, managed service provider | the person's own given name and surname | present |
| Built-in, service, shared mailbox, machine | empty | present |

A service account has no given name, and a machine account has no surname. Those fields are empty because the object states nothing there, and inventing a value would fabricate a fact. Read an empty `given_name` as an object that names no person, not as a value DataGen failed to fill.

`display_name` is unchanged and still repeats within a company, because repeated display names are a fact real directories contain.

## Identifier uniqueness

Identifier issuance is scoped the way each attribute is really scoped, and the generation-time invariants judge them on the same scope:

| Column | Scope of uniqueness | Why |
| --- | --- | --- |
| `user_principal_name` | the whole generated world | a principal name is a routable identifier and carries its own domain |
| `mail` | the whole generated world | a mailbox address is routable in the same way |
| `sam_account_name` | one root domain, not the world | the attribute carries no domain component precisely because it is unique within a domain and not beyond it; a second forest's `Administrator` is a real `Administrator` |
| `distinguished_name` | directory accounts, organizational units and groups, pooled across the world | a distinguished name states where an object sits, so it names exactly one object, whatever class that object is |

Group by `domain` together with `sam_account_name` when you need the unique key for that attribute. Grouping by `sam_account_name` alone will report cross-domain repeats that a real estate also contains.

`devices.distinguished_name` and `servers.distinguished_name` are outside that pool, permanently: each is a copy of the asset's own machine account's distinguished name rather than the name of a further object, so counting them again would report every domain-joined asset as a duplicate of itself.

### An object that sits in no directory tree

`accounts.distinguished_name` is empty for a cloud-joined device account — an `accounts` row whose `account_type` is `Device` and whose `identity_provider` is `EntraID`. A cloud-only object holds no position in a directory, so it has no distinguished name to state. Before v0.14.0 the column carried the bare host name, which names no position in a directory and so could not be judged for uniqueness at all; the value is now empty. A hybrid-joined device has both accounts: its on-premises machine account is a separate `accounts` row, is unaffected, and still carries a `CN=<hostname>` distinguished name naming its position. A cloud-only device has no such row, so the empty value is the only distinguished name it states.

Read the empty value as an object that sits in no directory tree, not as a value DataGen failed to fill. The uniqueness pool skips it for being blank, which is the honest reason to skip it.

### Organizational unit placement and derived group names

A department's organizational unit is now placed under the unit of the business unit that owns it. That placement is unconditional: it applies to every department whose business unit resolves, not only to a department whose name repeats. A repeated name affects one thing and one thing only — the label used in the names of the groups derived from that department. The two are separate changes and should not be read together.

Two business units of one company may each run a department of the same name. That is realistic and both names are kept — neither is numbered, and neither is rewritten. What changed is where the derived directory objects sit, and what the derived groups are called:

- A department's organizational unit is placed under the unit of the business unit that owns it: `OU=Legal,OU=Commercial,OU=Employees,DC=…` and `OU=Legal,OU=Technology,OU=Employees,DC=…`. The tree follows the organization chart, which is where a real directory holds it, and position rather than a suffix tells the two units apart. A tier of units that did not exist in v0.13.0 now appears between `OU=Employees` and the department units, one unit per business unit, carrying `purpose` `Business Unit Users`. These are new rows in `organizational_units`, not moved ones. Every department sits one level deeper than it did, and a department unit's own `name` is unchanged — only its `parent_ou_id` and `distinguished_name` differ. A department that resolved no owning business unit would still be placed directly under `OU=Employees`; the shipped catalogs give every department one, so in practice every department unit gains the level.
- Every group derived from a department is held in one container, so position cannot separate two of them and the common name must. Where a department name occurs once in the company, its groups keep the unqualified name they had. Where it repeats, the groups of each instance carry the owning business unit: `GG Commercial Legal Users` beside `GG Technology Legal Users`, and the same for the `DL`, `ACL FS`, `ACL MBX` and team groups derived from those departments. A world with no repeated department name sees no group name change at all.
- A group's distinguished name now escapes its common name component, which was previously interpolated raw. Account and organizational unit distinguished names already escaped theirs before v0.14.0, so this brings groups into line rather than introducing escaping to the export. A component holding a comma — or any of `+`, `"`, `\`, `<`, `>`, `;`, `=` — would otherwise read as more components than the object has.

  The shipped catalogs do contain values that would require escaping. `locality_reference` holds office city names containing commas and parentheses, and an office city becomes a `Location Users` unit name; `surnames_reference` holds the values `Trease,` and `Vernal;Cooper`, which would reach an account's common name through a person's display name. Both of those components already escaped before v0.14.0, so neither is new here. No shipped department or organization-template name carries such a character, so the group change itself is not expected to move a value in a world generated from the shipped catalogs.

  Whether any given world contains an escaped component depends on which catalog rows its seed draws, and a world may well contain none — a comma-bearing city or surname has to actually be selected. Treat escaping as a property of the format rather than as something a particular export is guaranteed to exhibit: parse a distinguished name rather than splitting it on commas, because that is the case this protects against, whether or not the export in front of you happens to contain one.
- A business unit's name is now unique within its company, because nothing above a business unit distinguishes two of them. A scenario asking for more business units than the catalog has distinct names for will see the surplus suffixed, as departments already were within a business unit.
- Two departments of the same name previously shared one organizational unit, so the people of the second were held in the first's unit. Each department now has its own unit and its own people.

No `accounts.distinguished_name` moves. A person's account is parented by the `Location Users` unit for their office, and location units did not move — that is the whole reason. Office assignment always succeeds, because every person is assigned an office from the company's office list and a `Location Users` unit is created for every distinct office city drawn from that same list, so the container precedence never falls through to its department-unit branch for a person account. Built-in, service, administrative and machine accounts sit in their own branches and are likewise unaffected.

So a consumer holding distinguished names captured from a v0.13.0 export will find new values in exactly two places: `organizational_units.distinguished_name` for every department unit, and `groups.name` and `groups.distinguished_name` for the groups of a department whose name repeats in its company. Accounts keep every distinguished name they had. Separately, `organizational_units` carries a tier of `Business Unit Users` rows that did not exist before — new rows to read, not changed values.

The operative change was making principal-name issuance world-scoped, where it had previously been scoped per company. Mailbox uniqueness follows from it: every mailbox-enabled account takes its own principal name as its mail value, so unique principal names produce unique mail values. The mail registry, the `duplicate_account_mail` metric and the invariant behind it are defence in depth against a path no valid scenario reaches; they are not what makes mailboxes unique. The duplicate mailbox values seen before v0.13.0 were a symptom of company-scoped identifier issuance.

Two directory accounts never share a principal name, a mail value or a distinguished name in a generated world, including the ownership conditions below. Where a condition is about two objects naming one person, it is the name evidence and the person link that conflict, never an identifier.

## Account ownership conditions

`identity.accountOwnershipConditionCount` is an opt-in switch on the identity profile. It defaults to `0`, which emits none of these objects, and is bounded at `25`. Scenario validation rejects a value outside that range, and rejects a nonzero value the largest company cannot supply the people and shared mailboxes for.

Each unit of the count adds, per company, seven account objects and one set of shared-mailbox memberships. Every object is identifiable from the emitted record alone, without knowing which generator produced it:

| Condition | What the emitted record carries |
| --- | --- |
| Held secondary | the person's own given name and surname, the person's employee link, its own identifiers, and a description naming the primary account it sits beside |
| Conflicting holder | name attributes, `sam_account_name` and `mail` that all name a former holder the directory keeps no person record for, while `person_id` links the person who now uses it |
| Second primary | a second object shaped exactly like a primary account, carrying the same holder's employee identifier, so neither record declares which of the two is the primary |
| Disabled | a former primary retained rather than deleted, `enabled` false, with the created, modified, last-logon and password dates a retained object carries |
| Unlinked secondary | a real given name and surname with no `person_id` at all |
| Ownerless | a retained service account with no person link, no name attributes, and a description stating that no owner is recorded |
| Free-text owner | ownership stated only as prose in `description`, naming a team and a contact; no identifier is emitted for either, because the directory holds none |
| Shared access | an existing shared mailbox, with real group memberships added for several named people, and a description stating that access is held by named people |

Three of these are deliberately negative cases, present so that a consumer which trusts one field over another gets them wrong:

- **Conflicting holder** — the name evidence names one person and the link names another. Both are on the object, they disagree, and that disagreement is the object.
- **Second primary** — nothing on either object says which one is the primary. A consumer that assumes one object per person has no field to settle it with.
- **Unlinked secondary** — the object carries a person's name and no link to that person. The named person keeps their own primary account and its link.

The remaining conditions are ordinary directory facts rather than traps: a person genuinely holding a second account, a disabled object retained after it was superseded, a service account whose owner the directory never recorded, and one whose only ownership record is prose.

Shared access is not a multi-owner field. DataGen adds real group memberships from real people to shared mailboxes the company already has, so the access is a membership fact rather than an assertion. No mailbox is created for it.

Primary accounts are untouched. These conditions add objects beside the existing population: no person's primary account changes, no existing link is rewritten, and the person count is unchanged. A company that cannot supply the people or the shared mailbox a condition needs emits that condition fewer times, because neither is invented to reach the count.

## Organizational unit directory object security

An organizational unit carries the security-descriptor facts of the directory object itself. These are distinct from the file and registry security descriptors shipped as policy settings in the Windows policy families above: different source, different object, different consumer.

### The one shape for an entry on an organizational unit

- **Which rows are entries on an organizational unit**: exactly those whose `access_control_evidence.target_type` is `DirectoryOrganizationalUnit`. Their `target_id` is an `organizational_units.id`. No other `target_type` ever denotes an organizational unit, so the target type alone separates the two concepts and nothing has to be inferred from which part of the world wrote the row.
- **The mirroring container is not a second place to look**: an organizational unit is also carried in `containers` so that a policy can be linked to it, but security entries are held against the unit. A `target_type` of `Container` names a container that is not an organizational unit — a directory domain, a default directory container such as `CN=Users`, an Entra administrative unit, an Azure subscription or resource group, an Intune tenant.
- **`ApplyGroupPolicy` is an entry on the policy**, not on a unit. It is the right that security filtering is made of, it exists only on a policy object's security descriptor, and it carries `target_type` `Policy`.
- **`access_control_evidence.inheritance_scope` is always present on those rows.** It is one of `ThisObjectOnly`, `ThisObjectAndAllDescendants` or `NotRecorded`, and never empty when `target_type` is `DirectoryOrganizationalUnit`.
  - `NotRecorded` means the entry was read from the unit's security descriptor but the propagation flag it carried was not collected. It states that how far the entry reaches is **not known** — not that it reaches nothing. Reading it as `ThisObjectOnly` is a guess, and so is reading it as `ThisObjectAndAllDescendants`. The value exists so a single row says this itself rather than leaving an empty field to be interpreted.
  - A resolved scope appears where the unit an entry sits on was chosen for a reason that fixes how far it reaches. Those entries are deliberate and few: an entry set once at a subtree root to reach everything below it, an entry that applies to the unit object alone, and an entry set directly on a unit whose access control list is protected from inheritance.
  - Every other delegation carries `NotRecorded` — `ResetPassword`, `ReadLapsPassword`, `ReadUserProperties`, `WriteUserProperties`, `WriteGroupMembership`, `LinkGpo`, `CreateComputerObject`, `DeleteComputerObject`, `CreateChild`, `DeleteChild`, `CreateGroupObject`, `ReadPolicy`, `RemoteAssist`. DataGen does not resolve these, because nothing it collected says which flag was set. It would be tempting to resolve a right naming something a unit does not itself have, such as a password or a user property, on the grounds that applying to the unit alone would grant nothing; that argues about the right rather than about the flag, and it contradicts the explicit-only rule below, since these delegations are set explicitly on every unit of their family and an entry repeated the whole way down is not one that was set to propagate.
- For other target types — a policy, an application, a repository — `inheritance_scope` may be null, because the system the entry came from has no container hierarchy for a scope to describe.
- `organizational_units.dacl_inheritance_protected`: true when the unit's discretionary access control list is protected from inheritance, so no inheritable entry set above it reaches it or anything below it. This is the `SE_DACL_PROTECTED` bit of the object's own security descriptor.
- `access_control_evidence.is_inherited` and `inheritance_source_id` are carried for the systems that report an entry as inherited and name what it came from, which is how SharePoint, Teams and Azure role assignments report theirs. Active Directory entries are collected explicit-only, so a directory entry is never marked inherited: on a directory row, `is_inherited` false means the entry is set on the object itself, and how far it then reaches is `inheritance_scope`, not this column.

`dacl_inheritance_protected` is not Group Policy link inheritance blocking. That is a separate, independent aspect of the same object, carried on `EnvironmentContainer.BlocksPolicyInheritance`, and a unit may have either, both or neither. No access control entry names a right containing `BlockInheritance`, because no collection method produces one.

### Only explicit entries are emitted

An entry that reaches a descendant by inheritance is stored once, on the object it is set on, and is not repeated further down. That is what a directory collector reads; storing it again on every descendant would repeat one fact many times.

Effective access on a unit is therefore derived by the consumer rather than read off a row. Select the rows whose `target_type` is `DirectoryOrganizationalUnit`, walk `parent_ou_id` upwards from the unit, honour each entry's `inheritance_scope`, and stop at the first ancestor-or-self whose `dacl_inheritance_protected` is set. An entry whose scope is `NotRecorded` cannot be resolved either way from the data, so a derivation should carry it through as unresolved rather than silently pick a reading. The walk begins at the topmost organizational unit: an entry on the domain object itself is a `Container` row and is outside the unit chain.

The generated hierarchy carries the four conditions that make that walk exercisable: an entry at a parent that inherits downwards, an entry on the same unit that applies to that object only, a unit partway down the tree with inheritance protection enabled, and real descendants both above and below it. The inheriting and this-object-only entries sit on the same unit deliberately, so scope is the only thing separating them: were scope ignored, both would appear to reach the child and the difference would be invisible.

## Directory account configuration items

The `configuration_items` artifact carries one item per directory account, alongside the platform, application, server, device, network, telephony, database, file share and collaboration items it already held. An account item has `ci_type` `Identity`, `source_entity_type` `DirectoryAccount`, `source_entity_id` set to the account's identifier, and a `ci_key` of the form `directory-account:<account id>`. Its `ci_class` follows the account class — `UserAccount`, `SecondaryAccount`, `PrivilegedAccount`, `ServiceAccount`, `SharedMailboxAccount`, `BuiltInAccount`, `MachineAccount`, `GuestAccount`, `ContractorAccount` or `ManagedServiceProviderAccount`.

Ownership is carried on both sides of the split this export already uses, because the two answer different questions:

| Side | Column | For an account item |
| --- | --- | --- |
| Canonical | `configuration_items.business_owner_person_id` | the account's resolved person link, unchanged |
| Observed | `cmdb_source_records.observed_business_owner` | the name a discovery source read off the object: its `given_name` and `surname` as text |

A source reads attributes; it does not resolve links. That is why the observed side carries name text rather than an identifier, and why the two sides can differ:

- For an ordinary user account the two agree.
- For a service, machine, shared or built-in account neither side carries an owner, because the object states none. No owner, technical owner or support group is invented for it.
- For a **conflicting holder** object the two genuinely disagree: the canonical side carries the linked person, the observed side carries the former holder's name. That disagreement is a property of the object, not an inconsistency in the export.

`technical_owner_person_id` is populated only for an invited account, from the person behind the sponsoring account, because a sponsor is the only party a directory records as answerable for an object it did not create for one of its own people. `support_team_id` is never set on an account item: a directory holds no support group for an account object. `notes` carries the object's own `description` verbatim, and nothing is read out of that prose into an owner column.

The existing source-record realism degradation still layers on the observed side unchanged, so observed values on an account item vary by source system the same way they do for every other item class.

## Scenario rejections

Two scenario shapes are rejected at validation rather than generating data that does not match their author's intent.

### A retired option

A scenario that still sets an option DataGen no longer reads used to deserialize cleanly with the option silently dropped, then generate data its author did not ask for, with nothing reported. Validation now reports a `retired-scenario-option` error naming the option, the version that retired it and its replacement, and scenario loading refuses the document outright rather than only warning about it.

| Retired option | Retired in | Replacement |
| --- | --- | --- |
| `identity.legacyDirectoryIdentifierVariantCount` | `0.13.0` | the account ownership conditions described above, opted into through `identity.accountOwnershipConditionCount` |

That option existed only in unreleased work and was never published, so no released version is affected and no scenario in use needs to change.

A property that is merely unknown is still accepted. Only a property registered as retired is rejected, so forward-compatible fields and third-party additions keep working exactly as before.

### Companies that resolve to one primary domain

Two companies whose names reduce to the same primary domain are rejected, with a `company-primary-domain-collision` error naming every company in the colliding group and the domain they resolved to.

Such a world previously generated cleanly and was impossible. Principal names and mail were disambiguated by world-scoped issuance, but a distinguished name is derived from directory position and was not: the second company's built-in `Administrator` carried a `sam_account_name` of `Administrator2` while its distinguished name stayed byte-identical to the first company's. Two directory objects cannot share a distinguished name.

Distinguished names are deliberately not rewritten to dodge the collision. A distinguished name describes where an object really sits, and renaming it to avoid a clash would fabricate the fact the rejection exists to prevent. Rename all but one of the colliding companies so their names no longer reduce to the same domain label.

## Export schema 2.2.0

The normalized export schema stands at `2.2.0`. It advanced from `2.1.0` to `2.2.0` in v0.13.0, which added five columns:

| Table | Column |
| --- | --- |
| `accounts` | `given_name` |
| `accounts` | `surname` |
| `accounts` | `description` |
| `organizational_units` | `dacl_inheritance_protected` |
| `access_control_evidence` | `inheritance_scope` |

v0.14.0 adds no column, removes none and moves none, so the schema version is unchanged at `2.2.0`. There is no new column to look for. What v0.14.0 moved is the value carried in columns that were already exported, and the notes below say which.

### Consumer compatibility

The additions are purely additive, and all five columns are appended at the end of their table, so no existing column changes position. An adapter that reads by column name is unaffected, and so is one that reads by column index: every previously exported column keeps the index it had.

An export produced before v0.13.0 carries none of these columns. Treat their absence as a dataset without that evidence rather than as objects reported to have no name attributes, no inheritance scope and no inheritance protection. Within an export that has them, an empty value is the object's own statement rather than a gap: `given_name` and `surname` are empty for an account class that names no person, and `inheritance_scope` is null only for a target type with no container hierarchy for a scope to describe — never for an entry on an organizational unit.

Two changes since v0.13.0 move existing values rather than adding columns, and neither adds or removes a column:

- `inheritance_scope` can now carry `NotRecorded`. An adapter that treated the column as a two-value vocabulary must accept the third value; one that already passed the string through needs no change. The value replaces what would otherwise have been an empty field on an entry on an organizational unit, so no row loses information.
- An entry on an organizational unit now carries `target_type` `DirectoryOrganizationalUnit` where a delegation entry previously carried `Container` with the identifier of the container that mirrors the unit. An adapter that resolved such a `Container` row through `containers.source_entity_id` to reach the unit should now read `target_id` directly. `Container` rows that name something other than an organizational unit are unchanged.

Directory account configuration items add no column. `configuration_items` and `cmdb_source_records` already carried every field they use and both were already exported, so an adapter reading those artifacts sees additional rows of new `ci_class` values and nothing else. An adapter that enumerates classes explicitly should add the account classes listed above; one that passes `ci_class` through needs no change.

The `Domain Controller Audit Baseline` policy object likewise adds rows, not columns: one more `GroupPolicyObject` per company in `policies`, and its settings in `policy_settings`.

## Reproducing an export across DataGen versions

A fixed scenario, seed, generation time and export timestamp reproduce an export byte for byte within one DataGen version. They do not carry that guarantee across versions, and v0.14.0 is a release where they do not.

The configuration management layer draws more values from the shared random source than it did in v0.13.0, and it runs before two other layers, so those layers' generated values shift in a world that has configuration management enabled. Row counts are unchanged — no entity appears or disappears because of it — but the values differ. An export produced by v0.13.0 is therefore not reproducible from v0.14.0, in addition to the column values listed above that moved for their own reasons.

If you keep an export as a fixed reference, regenerate it under v0.14.0 and retain the new one, together with the scenario, catalog and version identity that produced it. The DataGen version is already one of the inputs a reproducibility claim has to hold fixed; see [Reproducibility prerequisites](/getting-started/understanding-output#reproducibility-prerequisites).
